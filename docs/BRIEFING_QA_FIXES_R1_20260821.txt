## FIX 3 (P2, Idempotenz-Lücke): Event VOR Verarbeitung speichern
Datei: web/src/pages/api/stripe/webhook.ts
Aktuell: Verarbeitung (is_pro=true) passiert ZUERST (Zeilen 60-76), Event-Speicherung DANACH (Zeilen 80-85). Crash zwischen beiden → doppelte Verarbeitung.
FIX: Reihenfolge ändern:
1. Idempotenz-Check: `stripe_events` select id → wenn existiert: 200 return (bleibt)
2. Event-Speicherung: `stripe_events.insert({id, type, status: "processing"})` VOR der Verarbeitung
3. Dann Verarbeitung (checkout.session.completed → is_pro=true; subscription.deleted/updated → is_pro=false)
4. Danach `stripe_events.update({status: "processed"}).eq("id", event.id)`
- Bei Fehler in der Verarbeitung: status auf "error" setzen + 500 return (Event ist gespeichert → kein Doppel-Processing, aber sichtbar).

## FIX 4 (P2, UX/Leak): content_reports Duplikat → freundliche Meldung

BETROFFENE DATEIEN (Meldelink-Submit): web/src/pages/board.astro, web/src/pages/forum.astro, web/src/pages/forum/[id].astro, web/src/pages/chat.astro — suche nach `content_reports`-insert im Client-JS (`.from("content_reports").insert`).
FIX: In JEDEM betroffenen insert-Call: try/catch um den Supabase-Call; wenn `error` existiert UND die Fehlermeldung `content_reports_` (Constraint) oder `duplicate`/`unique` enthält → freundliche Meldung anzeigen: „Du hast diesen Inhalt bereits gemeldet." (i18n: data-de/data-en Muster wie bestehende Meldungen, Key z.B. melden.bereits_gemeldet). Andere Fehler → generische Meldung „Melden fehlgeschlagen. Bitte versuche es später."
